# AI 视频编排系统优化方案

## 1. 目标与本轮范围

本方案面向“用户一次上传多段洗车视频，系统理解全部素材并生成一条完整营销短视频”的工作流，目标是提高大文件处理可靠性、AI 请求可恢复性、并发一致性和前端状态同步效率。

本轮范围：

- 删除“复制项目”功能及其相关 UI、API、测试和文档；
- 多文件上传改为全量校验后一次提交；
- 大文件头部读取和哈希计算改为流式处理；
- 分片上传以 parts 表为唯一事实来源，避免并发丢更新；
- Relay SSE 采用分级响应额度、硬上限和增量解析；
- 降低模型流式进度写入 SQLite 的频率；
- 前端使用轻量 progress 查询，减少完整项目详情轮询；
- 保留 API 原始错误码、消息、可重试属性和阶段信息；
- 普通视频与带字幕视频分开记录渲染状态，失败时只重试未完成产物。

暂不处理：

- 生产环境身份认证和角色校验仍沿用当前本机 Demo 假设；
- 数据库索引优化暂缓，待有实际查询计划和规模数据后再处理。

## 2. 核心设计原则

### 2.1 AI 与确定性程序分工

AI 只负责：

- 语音转写内容理解；
- 关键画面理解；
- 每段素材的洗车广告作用标记；
- 基于全部素材分析结果提出播放顺序；
- 生成每段素材的可读内容说明。

确定性程序负责：

- 文件接收、哈希、媒体探测和资源释放；
- `clipId`、项目和租户边界；
- 任务状态、断点、重试、取消和幂等；
- 校验素材是否全部出现且仅出现一次；
- 根据 `finalClipOrder` 生成时间线；
- 读取原始片段并执行字幕、渲染和产物检查。

AI 不得决定删除素材、猜测文件路径、修改素材 ID 或直接写入最终时间线。

### 2.2 关键不变量

对于上传 `N` 段素材：

1. 最终素材集合长度必须为 `N`；
2. `finalClipOrder` 必须包含全部有效 `clipId`；
3. 每个 `clipId` 恰好出现一次；
4. 时间线只能引用本次任务的原始素材；
5. 每段素材都有内容说明和广告作用；
6. 任一中间步骤失败，不得产生用户无法解释的半提交状态；
7. 已完成的阶段可以在重启或重试后复用。

## 3. 推荐工作流

```mermaid
flowchart LR
    A["上传全部素材"] --> B["临时暂存"]
    B --> C["批量媒体校验"]
    C --> D["一次性提交素材清单"]
    D --> E["逐段转写与关键画面分析"]
    E --> F["AI 生成广告作用与内容说明"]
    F --> G["确定性校验分析完整性"]
    G --> H["AI 生成 finalClipOrder"]
    H --> I["确定性生成时间线"]
    I --> J["生成字幕与渲染产物"]
    J --> K["输出探测与交付"]
```

### 3.1 素材接收阶段

素材接收采用两阶段提交：

#### 阶段一：暂存和校验

所有文件先写入临时目录，不修改项目正式状态。每个文件完成：

- 大小限制检查；
- 文件头 MIME 检查；
- 流式 SHA-256 计算；
- ffprobe 媒体探测；
- 分辨率、时长、编码检查；
- 缩略图或关键帧生成；
- 临时结果记录。

任一文件失败时，清理本批次临时资源并返回批量失败结果。

#### 阶段二：一次性提交

只有所有文件校验成功后，才执行：

- 写入素材表；
- 更新项目 `assetIds`；
- 更新项目状态；
- 写入审计记录；
- 将临时文件原子 rename 到正式目录。

数据库变更使用事务；文件系统操作使用临时目录和补偿清理，避免出现“接口失败但部分素材已保存”。

## 4. 删除复制项目功能后的资产模型

删除复制项目后，资产关系简化为：

```text
一个 assetId
  → 一个 projectId
  → 一个不可变 originalPath
```

不再维护：

- `sourceAssetId` 跨项目引用；
- 副本项目的素材复用；
- 源项目和副本项目之间的文件生命周期；
- 复制项目的引用计数或硬链接清理逻辑。

项目删除时，可以在确认没有活动生成版本后，清理该项目的数据库记录、原始目录、临时目录和生成目录。

## 5. 大文件处理策略

### 5.1 头部读取

文件类型检测只读取前 16～32 字节，不得将整个视频加载到 Node.js 内存。

### 5.2 哈希计算

采用：

```text
临时文件
  → createReadStream
  → SHA-256
  → checksum
```

不要对 250 MB 级别文件执行整文件 `readFile`。

### 5.3 结果复用

上传流程中产生的结果应被后续步骤复用：

```text
partSha256[]
uploadSha256
mediaProbe
validationStatus
```

避免在上传、入库和生成阶段重复扫描同一个大文件。

### 5.4 验收指标

- 单文件内存占用不随文件大小线性增长；
- 多文件并发上传不会导致 Node 进程内存持续攀升；
- 哈希结果与原始文件一致；
- 取消或失败后临时文件可以清理；
- 文件系统中不会留下半成品目录。

## 6. 分片上传一致性

`video_upload_parts` 表作为分片状态的唯一事实来源，`completed_part_numbers` 只能作为缓存或展示字段。

### 6.1 分片写入

相同 `uploadId + partNumber` 的请求满足幂等性：

- 相同 SHA-256：直接返回成功；
- 不同 SHA-256：返回冲突；
- 不同分片并发写入：不能相互覆盖；
- 数据库和分片文件路径保持一致。

### 6.2 完成上传

完成操作必须重新从 parts 表计算：

1. 分片数量；
2. 分片编号是否连续；
3. 每个分片大小和 SHA-256；
4. 合计文件大小；
5. 合并后完整文件 SHA-256。

验证通过后，在同一事务中创建唯一 analysis task 并将上传会话标记为 completed。

并发 complete 请求只能创建一个分析任务，依靠租户范围内的幂等键约束保证。

## 7. AI 请求与 Relay 策略

### 7.1 分级响应额度

不设置过小的单一全局上限，而是按调用类型分级：

| 调用类型 | 建议软上限 | 建议硬上限 |
| --- | ---: | ---: |
| 单帧截图理解 | 1 MiB | 4 MiB |
| 单素材联合分析 | 2 MiB | 8 MiB |
| 全量素材编排 | 4 MiB | 16 MiB |
| 普通聊天测试 | 4 MiB | 16 MiB |

这些值是带冗余的初始值。上线后根据实际数据调整：

```text
硬上限 = max(当前 p99 响应大小 × 4, 4 MiB)
```

### 7.2 增量读取

Relay SSE 应使用增量解析：

- 按块读取响应；
- 维护有限大小的帧缓冲区；
- 统计累计响应字节数；
- 超过硬上限时主动取消请求；
- 保留原始错误码、错误消息和 retryable 属性。

不能无限累积完整响应字符串。

### 7.3 模型日志写入节流

模型流式进度建议按以下节点持久化：

- 请求创建；
- 首字节到达；
- 每 100～250 ms 最多一次；
- 阶段变化；
- 完成或失败。

实时进度只保留最近快照，完整模型响应在请求结束后保存一次，避免 token 级 SQLite 同步写入。

### 7.4 AI 输出校验

模型响应必须经过 Schema 校验和语义校验：

- 未知 `assetId` 拒绝；
- 重复 `assetId` 拒绝；
- 缺少素材拒绝；
- `order` 不连续拒绝；
- `marketingRole` 不在允许枚举中拒绝；
- 解析失败只允许有限次数修复；
- 修复失败保留原始响应错误。

## 8. 错误合同

服务端统一返回：

```json
{
  "code": "EDIT_PLAN_INVALID",
  "message": "模型生成的编排计划不完整",
  "retryable": false,
  "stage": "planning",
  "details": {},
  "traceId": "..."
}
```

服务端不得把所有错误统一改成 `INVALID_UPLOAD`。前端根据 `code` 映射为用户文案，例如：

| 原始错误 | 用户提示 |
| --- | --- |
| `relay_http_503` | 模型服务暂时不可用，系统将自动重试 |
| `EDIT_PLAN_INVALID` | 编排计划不完整，请重试 |
| `MEDIA_PROBE_FAILED` | 视频媒体信息无法读取，请更换文件 |
| `checkpoint_concurrent_update` | 任务状态发生更新，请重新加载 |

这样既保留机器可诊断性，也能向用户提供可理解的提示。

## 9. 生成状态和断点

生成版本的状态应体现可恢复阶段：

```text
queued
→ probing
→ analyzing
→ planning
→ timeline_ready
→ rendering
→ completed
```

失败状态必须记录：

- 失败阶段；
- 原始错误码；
- 原始错误消息；
- 是否可重试；
- 当前重试次数；
- 下一次重试时间；
- 已完成素材检查点。

重试只从最近一个未完成检查点继续，不重新处理已经成功的素材。

## 10. 渲染产物拆分

将渲染拆成独立产物：

```text
captions.json
captions.vtt
output.mp4
output-captioned.mp4
output-inspection
```

对应状态拆分为：

```text
captions
plainRender
captionedRender
inspection
```

如果普通视频已完成、带字幕视频失败，下一次只重试带字幕视频，不重复渲染普通视频。

只有字幕、普通视频、带字幕视频和输出探测全部通过，版本才标记为 completed。

## 11. 前端状态同步

### 11.1 轮询接口

生成期间只查询轻量 progress 数据：

```text
generationId
status
progress
currentStep
steps
retryState
error
updatedAt
```

完整项目详情只在以下时机刷新：

- 上传完成；
- 删除素材；
- AI 分析完成；
- 编排计划完成；
- 时间线完成；
- 渲染完成；
- 用户主动查看详情。

### 11.2 轮询节奏

```text
可见页面：1.2 秒 → 2 秒 → 3 秒 → 5 秒
页面隐藏：暂停
retry_waiting：根据 nextRetryAt 调度
终态：停止
```

如果将来需要实时更新，再考虑 SSE；当前轻量 progress 查询已经可以显著降低传输量和数据库反序列化压力。

## 12. 分阶段实施计划

### 阶段 0：建立基线

只测量，不改变业务行为：

- 单文件和多文件上传耗时；
- Node 内存峰值；
- Relay 响应大小 p95/p99；
- SQLite 进度写入次数；
- 前端轮询流量；
- 普通视频和字幕视频渲染耗时。

### 阶段 1：素材接收可靠性

- 删除复制项目功能；
- 两阶段多文件上传；
- 流式哈希；
- 分片并发幂等；
- parts 表唯一事实来源；
- 文件和数据库补偿清理。

### 阶段 2：AI 请求边界

- 分级 Relay 响应额度；
- 增量 SSE 解析；
- 进度写入节流；
- 原始错误透传；
- 结构化响应 Schema 校验。

### 阶段 3：编排与恢复

- 全量素材汇总；
- AI 只生成 `finalClipOrder`；
- 确定性校验素材集合；
- 生成版本检查点；
- 失败阶段级重试。

### 阶段 4：渲染与前端

- 普通/字幕渲染状态拆分；
- 只重试未完成产物；
- 前端改用 progress 轮询；
- 页面隐藏暂停请求；
- 终态停止轮询。

## 13. 验收标准

### 素材和上传

- 第二个文件失败时，第一个文件不会残留到项目；
- 并发上传不同分片不会丢失完成状态；
- 并发 complete 只创建一个分析任务；
- 大文件处理不会整文件加载到内存；
- 失败和取消后临时文件可以清理。

### AI 和编排

- 所有素材均有内容说明和广告作用；
- `finalClipOrder` 长度等于素材数量；
- 所有素材恰好出现一次；
- 模型返回未知或重复 ID 时任务不会进入渲染；
- 超大 Relay 响应会被限制且不会无限占用内存；
- 正常响应不会因额度过小被误截断。

### 渲染和交付

- 普通视频和带字幕视频可以独立恢复；
- 普通视频成功、字幕视频失败时不会重复渲染普通视频；
- 输出文件通过媒体探测后才标记 completed；
- 时间线严格按 `finalClipOrder` 读取原始片段。

### 前端

- 生成期间不持续下载完整项目详情；
- 页面隐藏后停止轮询；
- retry_waiting 使用下一次重试时间调度；
- 完成、失败、取消后停止轮询；
- API 原始错误可以在诊断视图中定位。

## 14. 后续再评估事项

以下内容不纳入当前阶段：

- 真实生产身份认证与角色权限；
- 数据库索引和查询计划优化；
- SSE/WebSocket 实时进度替代方案；
- 跨项目素材复用；
- 对象存储迁移和 CDN；
- 分布式任务队列。

这些事项应在有明确部署环境、数据规模和运行指标后再单独设计。
