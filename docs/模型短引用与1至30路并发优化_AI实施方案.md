## 3. 已确认的当前问题

### 3.1 真实故障

生成版本曾在智能编排阶段连续调用模型三次。三次响应都满足以下条件：

- 返回 17 条素材；
- 17 个真实 `assetId` 均正确；
- 没有遗漏和重复；
- `order` 为 1 至 17；
- 营销顺序和理由均已生成。

但模型三次都改写了随机长字符串 `projectId`，分别出现字符替换、混入其他 Unicode 字符或截断，因此服务端最终返回：

```text
EDIT_PLAN_INVALID
```

这证明失败不是营销编排能力不足，而是让模型复制程序主键造成了错误的失败条件。

### 3.2 `assetId` 的同类风险

虽然本次 17 个 `assetId` 恰好正确，但当前设计要求模型在一次输出中完整复制、识别并排序最多 50 个随机长 ID。素材越多，越容易发生：

- 字符替换；
- Unicode 混入；
- 字符串截断；
- 漏素材；
- 重复素材；
- 语义内容与 ID 错配。

因此不能只删除 `projectId` 校验，必须让真实 `assetId` 同样退出模型输入输出边界。

### 3.3 当前并发限制不是单点配置

当前“画面理解并发”至少存在以下边界：

| 位置 | 当前行为 |
| --- | --- |
| `src/shared/auto-video-contracts.ts` | 前端选项只有 `[1, 2, 3, 4]` |
| `analysisProfileSchema` | `visualConcurrency` 最大为 4 |
| `autoVideoGenerationCreateSchema` | 创建请求最大为 4 |
| `src/server/auto-video-worker.ts` | `MAX_AUTO_VIDEO_VISUAL_CONCURRENCY = 4` |
| `src/server/index.ts` | 模型总并发快照最大为 20 |
| Worker `modelSemaphore` | 使用独立环境变量和默认值，可能继续把 30 路请求限制在更低水平 |

只改前端下拉框会被 API 拒绝；只改 Schema 会被 Worker 的视觉信号量限制；只改视觉信号量仍可能被模型总信号量限制。实施必须统一全部边界。

## 4. 锁定的产品与架构决策

以下决定已经确定，实施 AI 不得另行设计相反方案：

1. 真实 ID 保留，模型短引用不是数据库主键。
2. 模型不返回 `projectId`。
3. 模型不返回真实 `assetId`。
4. 单素材模型调用不需要返回任何身份字段；服务端使用当前调用上下文附加身份。
5. 批量模型调用使用 `clip_001`、`clip_002` 等短引用。
6. 短引用由服务端根据当前版本权威素材数组确定性生成。
7. 初次请求和修复重试必须复用同一映射。
8. 第一版成片必须使用全部有效素材，每个恰好一次。
9. `excludedAssets` 退出模型协议；内部持久化对象继续由服务端写入空数组以保持兼容。
10. 模型只决定语义、角色、顺序和理由；服务端决定身份、归属和完整性。
11. 内部持久化 `EditPlan`、时间线和 Remotion 合同继续使用真实 `assetId`。
12. 画面理解并发允许整数 1–30，默认仍为 1。
13. 进程级总视觉并发和总模型并发必须限制多个项目的合计请求数。
14. FFmpeg、ASR 和 Remotion 不跟随画面理解并发无条件扩大到 30。

## 6. 目标数据流

```mermaid
flowchart LR
    A["generation.assetIds 中的真实 ID"] --> B["服务端创建 ModelAssetReferenceMap"]
    B --> C["构造仅含 clipRef 的模型输入"]
    C --> D["模型返回 clipRef 语义或顺序"]
    D --> E["服务端严格校验短引用全集"]
    E --> F["映射回真实 assetId"]
    F --> G["服务端附加真实 projectId"]
    G --> H["内部 Schema 校验"]
    H --> I["持久化、时间线、字幕、渲染"]
```

模型日志仍可通过模型调用的服务端审计上下文记录真实 `projectId/generationId/assetId`，但这些值不得出现在发送给模型的正文或要求模型返回的 JSON 中。

## 7. 第一步：新增短引用映射模块

建议新增：

```text
src/server/model-asset-reference.ts
```

建议合同：

```ts
export type ModelClipRef = `clip_${string}`;

export type ModelAssetReferenceMap = {
  readonly byAssetId: ReadonlyMap<string, ModelClipRef>;
  readonly byClipRef: ReadonlyMap<ModelClipRef, string>;
};

export const createModelAssetReferenceMap = (
  assetIds: readonly string[],
): ModelAssetReferenceMap;
```

要求：

- 输入顺序来自当前生成版本权威素材顺序。
- 生成 `clip_001` 至 `clip_050`。
- 至少三位补零。
- 输入为空、包含空 ID、包含重复 ID 或超过素材上限时拒绝。
- 映射是纯函数，便于直接单元测试。
- 不使用文件名、数组索引数字或模型生成文本作为反向映射依据。
- 不把映射写进数据库；持久化结果只保存真实 ID。

可以增加辅助函数，但每个函数必须单一职责，例如：

```ts
toModelClipRef(assetId)
toAssetId(clipRef)
mapAssetAnalysesForModel(analyses)
hydrateEditPlan(candidate, projectId)
```

## 8. 第二步：模型专用 Schema 与内部 Schema 分离

不要修改内部 `EditPlan` 让全系统改用短引用。应新增服务端私有的模型 DTO Schema。

### 8.1 模型编排输入 v2

```json
{
  "schema": "auto-video-edit-plan-input.v2",
  "clips": [
    {
      "clipRef": "clip_001",
      "durationMs": 4200,
      "marketingRole": "hook",
      "roleReason": "提问口播吸引注意",
      "audioSummary": "你的车多久没有深度清洁了",
      "visualSummary": "车辆进入洗车门店",
      "people": [],
      "scenes": ["洗车门店"],
      "screenTexts": [],
      "chronologicalHints": []
    }
  ],
  "canvas": {
    "width": 1080,
    "height": 1920,
    "fps": 30
  },
  "userInstruction": "按口播叙事优先编排",
  "allClipsMustBeUsed": true
}
```

输入正文禁止出现：

- `projectId`
- `generationId`
- 真实 `assetId`
- tenant/owner 身份
- 本地路径
- 媒体签名 URL

### 8.2 模型编排输出 v2

```json
{
  "clips": [
    {
      "clipRef": "clip_003",
      "order": 1,
      "reason": "结果画面配合问题口播，先建立吸引力"
    },
    {
      "clipRef": "clip_001",
      "order": 2,
      "reason": "进入门店后承接服务介绍"
    }
  ],
  "overallReason": "按照吸引注意、服务介绍、洗车过程、效果展示和行动引导组织"
}
```

输出删除：

- `projectId`
- 真实 `assetId`
- `excludedAssets`

模型 response format 必须与这个输出完全一致，使用严格对象和 `additionalProperties: false`。

### 8.3 转换为内部 EditPlan

模型短引用候选通过校验后，由服务端构造：

```ts
const editPlan = editPlanSchema.parse({
  projectId: authoritativeProjectId,
  clips: candidate.clips.map((clip) => ({
    assetId: referenceMap.byClipRef.get(clip.clipRef),
    order: clip.order,
    reason: clip.reason,
  })),
  excludedAssets: [],
  overallReason: candidate.overallReason,
});
```

这里的 `authoritativeProjectId` 必须来自 `plan()` 的服务端输入，不得来自模型候选。

## 9. 第三步：统一改造所有模型身份字段

只改 `plan()` 不算完成。必须检查并改造所有模型业务边界。

### 9.1 单素材视觉分析

一次调用只处理一个素材，模型输出 Schema 删除 `assetId`。解析成功后由服务端附加当前调用的权威 ID：

```ts
const content = modelAssetVisualContentSchema.parse(candidate);
return assetVisualAnalysisSchema.parse({
  ...content,
  assetId: expectedAssetId,
});
```

视觉修复请求也不得让模型复制真实 ID。

### 9.2 单素材综合理解

模型输出删除 `assetId`。服务端附加当前素材 ID，并继续执行现有 `combinedSummary` 规范化。不能接受模型返回另一个素材的 ID。

### 9.3 整批 MarketingRole 判断

把模型输入输出中的真实 `projectId/assetId` 改为 `clipRef`：

```json
{
  "schema": "auto-video-marketing-role-batch-input.v2",
  "clips": [
    {
      "clipRef": "clip_001",
      "transcript": "你的车多久没有彻底洗过了？",
      "visualSummary": "工作人员向车辆喷洒清洁液"
    }
  ]
}
```

模型输出：

```json
{
  "clips": [
    {
      "clipRef": "clip_001",
      "marketingRole": "hook",
      "roleReason": "提问口播用于开场吸引注意"
    }
  ]
}
```

服务端完成引用校验后转换为现有内部 `MarketingRoleBatchResult`，并附加真实 `projectId/assetId`。现有九类角色、口播优先规则和持久化字段保持不变。

### 9.4 智能编排

`plan()` 的推荐控制流：

```text
验证服务端输入素材集合
  → 创建一次短引用映射
  → 构造 v2 模型输入
  → 调用模型
  → 解析 v2 模型输出
  → 校验短引用全集和顺序
  → 转换为真实 assetId
  → 服务端附加 projectId / excludedAssets
  → 使用内部 editPlanSchema 校验
  → 返回 EditPlan
```

本地无 Relay 的确定性降级路径可以直接使用真实 ID 构造内部 `EditPlan`，因为它没有模型边界；也可以复用短引用转换函数，但不得增加不必要复杂度。

## 10. 第四步：严格校验和具体修复错误

短引用输出必须检查：

1. 输出数量等于输入素材数量。
2. 每个 `clipRef` 都存在于当前映射。
3. 每个 `clipRef` 恰好出现一次。
4. 不允许未知引用。
5. 不允许重复引用。
6. 不允许遗漏引用。
7. `order` 从 1 开始连续递增。
8. `order` 与数组位置一致。
9. 映射后的真实 ID 集合与权威素材集合完全一致。
10. 每条 `reason` 和 `overallReason` 满足现有长度及非空约束。

建议定义本地类型化错误：

```ts
type EditPlanValidationError = Error & {
  code: 'EDIT_PLAN_INVALID';
  retryable: false;
};
```

消息必须包含具体原因，例如：

```text
EDIT_PLAN_INVALID: missing clipRef: clip_017; duplicate clipRef: clip_006; unexpected clipRef: clip_099
```

修复循环要求：

- 最多三轮，沿用现有产品行为。
- 每次复用原短引用映射。
- 下一轮输入携带上一轮具体校验错误。
- JSON 解析失败和业务集合校验失败可以进入受控修复。
- 网络错误、超时、429、SSE 中断等上游错误不得被当成 `EDIT_PLAN_INVALID`。
- 三轮后抛出最后一个具体校验错误，不再创建新的通用异常覆盖详情。

## 11. 第五步：并发范围统一为 1–30

### 11.1 共享常量

在 `src/shared/auto-video-contracts.ts` 建立单一事实来源：

```ts
export const AUTO_VIDEO_VISUAL_CONCURRENCY_MIN = 1;
export const AUTO_VIDEO_VISUAL_CONCURRENCY_MAX = 30;
export const AUTO_VIDEO_VISUAL_CONCURRENCY_DEFAULT = 1;

export const AUTO_VIDEO_VISUAL_CONCURRENCY_OPTIONS = Array.from(
  {length: AUTO_VIDEO_VISUAL_CONCURRENCY_MAX},
  (_, index) => index + 1,
);
```

如果 `as const` 与动态数组类型不兼容，使用只读 `number[]` 并让 Zod 承担运行时边界校验，不要手写 30 个数字。

### 11.2 Schema

以下字段允许整数 1–30：

```ts
visualConcurrency: z.number().int().min(1).max(30)
modelConcurrency: z.number().int().min(1).max(30)
```

历史版本的 `analysisProfile.visualConcurrency` 继续允许缺省；缺省时恢复为 1。已有 1–4 的历史快照继续合法。

创建接口必须拒绝：

- `0`
- `31`
- `1.5`
- `NaN`
- 字符串 `"30"`

不得把非法 API 输入静默修正为合法值。

### 11.3 前端

`AutoVideoApp.tsx` 中：

- 下拉框显示 1 至 30。
- 默认选中 1。
- 创建 AI 版本时继续发送数字 `visualConcurrency`。
- 文案明确：高并发更容易触发模型限流和网关错误，实际并发受全局上限控制。
- 不新增与现有设置抽屉重复的并发入口。

建议文案：

```text
默认 1 路。5 路以上会增加模型限流和网关压力；实际并发还受服务端全局模型上限控制。
```

### 11.4 Worker 和全局上限

实际画面模型并发必须是：

```text
min(
  版本选择的 visualConcurrency,
  剩余素材数量,
  AUTO_VIDEO_VISUAL_GLOBAL_CONCURRENCY,
  AUTO_VIDEO_MODEL_CONCURRENCY
)
```

建议环境变量：

```env
AUTO_VIDEO_VISUAL_GLOBAL_CONCURRENCY=30
AUTO_VIDEO_MODEL_CONCURRENCY=30
```

要求：

- `visualSemaphore` 使用全局视觉上限，而不是固定常量 4。
- `modelSemaphore` 限制当前进程内所有模型调用总数，包括视觉、素材理解和编排。
- 两个上限均严格解析为整数 1–30。
- 配置缺失时允许达到 30，但用户默认选择 1，因此单个默认版本不会突然发出 30 个请求。
- 多个版本并行时，全进程总量不得超过全局模型上限。
- `AUTO_VIDEO_WORKER_CONCURRENCY` 仍独立控制同时运行的生成版本数。
- `mediaSemaphore`、Qwen ASR 和 Remotion 渲染并发保持现有独立策略。

应避免“版本快照写了 30，Worker 实际永远只能跑 4 或 6”的假开放状态。

## 12. 第六步：高并发下的失败、取消和恢复

实施时验证并保持：

- 明确可重试的 429、502、503、504、超时和流中断使用现有受控重试。
- 如果上游提供 `Retry-After`，优先遵守。
- 重试可以增加指数退避和少量抖动，但不得改写上游错误内容。
- 用户取消后，正在执行及等待信号量的请求均能退出。
- 任一不可重试分支失败时，不再启动尚未开始的同批分支。
- 每条素材完成后仍保存检查点。
- 恢复时只重跑未完成素材，不重复覆盖已完成分析。
- 模型队列等待时间与请求执行时间分别记录，便于定位瓶颈。

不要为本任务新增哈希、合同冻结、快照基线或额外发布门禁；当前风险可以通过现有主键、严格 Schema 和普通回归测试覆盖。

## 14. 必须增加的自动化测试

### 14.1 短引用映射

- 17 个素材稳定生成 `clip_001` 至 `clip_017`。
- 50 个素材稳定生成 `clip_001` 至 `clip_050`。
- 输入重复真实 ID 时拒绝。
- 未知 `clipRef` 反向映射时拒绝。
- 初次请求和修复重试复用相同映射。

### 14.2 模型身份隔离

- 编排请求正文不包含真实 `projectId`。
- 编排请求正文不包含任何真实 `assetId`。
- MarketingRole 批量请求正文不包含真实 ID。
- 单素材模型输出不需要 `assetId`。
- 模型响应没有 `projectId` 仍可成功生成内部 EditPlan。
- 最终持久化结果仍包含正确真实 ID。

### 14.3 完整性

- 漏一个短引用时拒绝。
- 重复一个短引用时拒绝。
- 多出未知短引用时拒绝。
- Unicode 混入或截断的短引用被拒绝。
- `order` 不连续时拒绝。
- 全部短引用恰好一次时通过。
- 映射后的最终时间线包含全部真实素材，每个恰好一次。

### 14.4 错误修复

- 第一次遗漏时，第二次请求包含 `missing clipRef` 详情。
- 连续三次失败时抛出最后一个具体 `EDIT_PLAN_INVALID`。
- Relay 超时或 429 保留原始错误，不被转换成 `EDIT_PLAN_INVALID`。

### 14.5 并发边界

- `visualConcurrency: 1` 通过。
- `visualConcurrency: 30` 通过。
- `0`、`31` 和 `1.5` 被拒绝。
- 使用可控 Deferred Promise 证明单版本峰值不超过用户选择。
- 选择 30 且全局上限 30 时，峰值可以达到 30。
- 多版本并行时，进程总峰值不超过全局模型上限。
- 某分支失败后不再启动排队分支。
- 取消后执行中和等待中的分支全部停止。

- 不迁移数据库表。
- 不改写历史真实 ID。

- 已有合法 EditPlan 的恢复任务继续复用，不重复调用模型。

- 历史 v1 模型对话日志继续可读；新日志使用 v2 Schema 名称区分。

## 17. 明确禁止的错误实现

- 直接删除 `projectId` 校验，却继续信任模型返回的真实 `assetId`。
- 收到模型结果后无条件覆盖任何未知真实 `assetId`，从而掩盖漏项或重复项。
- 把真实 ID 截短后发送给模型，并把截短结果当作全局 ID。
- 使用数组位置直接生成最终时间线而不校验模型返回全集。
- 修改数据库中已有 ID 或批量迁移历史版本。
- 只把前端下拉框改到 30，不修改 Schema 和 Worker。
- Schema 接受 30，但信号量仍固定为 4 或默认最多 6。
- 把模型限流、网络错误或 SSE 中断包装成 `EDIT_PLAN_INVALID`。
- 高并发失败后重新运行全部已完成素材。
- 为通过测试而弱化“全部素材恰好一次”的不变量。

## 19. 完成标准

只有同时满足以下条件才能标记为完成：

- 所有模型业务正文都不要求模型复制真实 `projectId/assetId`。
