## 1. 一句话任务

从权利清晰的网络素材中准备一组洗车视频片段，使用本机 IndexTTS2 为各片段生成中文口播，制作“正常测试包”和“异常测试包”，再用它们完整验证：

`上传片段 → Qwen3-ASR 语音转文字 → AI 理解画面 → AI 标注广告作用 → 全量自动排序 → 生成字幕 → 导出无字幕/带字幕成片`

本任务的交付物是可重复使用的测试数据及测试记录，不是面向消费者发布的商业广告。

## 4. 网络素材选择与权利边界

### 4.1 来源优先顺序

按以下顺序选素材：

1. 用户自有、自拍且确认可用于软件测试的素材。
2. 明确标注 CC0、CC BY 或其他允许修改和测试使用的单个文件。
3. 已在 `素材_洗车可商用` 中保存来源证据、且执行当天再次复核许可的 Pexels/Coverr 文件。
4. 只有现有画面确实缺失时，才从素材站手动下载少量补充文件。

可用的 Creative Commons 备选示例：Wikimedia Commons 的 [Waschanlage.ogv](https://commons.wikimedia.org/wiki/File:Waschanlage.ogv)，文件页标注为 CC BY 3.0；使用时必须保存作者、许可链接，并在清单中写明裁切、静音、配音等修改。

### 4.2 执行当天必须重新检查的条款

- [Pexels License](https://www.pexels.com/license/) 当前说明图片和视频可以免费使用、允许修改、通常不要求署名，但禁止原样转售，也不能暗示画面中的人物或品牌为产品背书。
- [Pexels Terms of Service](https://www.pexels.com/terms-of-service/) 提醒：素材许可不等于已经解决商标、人物肖像、场地和其他第三方权利。应优先选择没有清晰人脸、车牌、商标和门店标识的画面。
- [Coverr License](https://coverr.co/license/) 当前许可页包含署名、第三方权利以及 AI 使用限制等条件。由于本任务会把画面交给 AI 做分析和评测，新下载的 Coverr 素材在未确认条款适用性前不要使用；已有 Coverr 文件也只能在复核后纳入测试包。

许可页面可能变化。交接执行者必须以实际下载日期看到的正式页面为准，不得只引用本文件的概述。

### 4.3 每个源文件必须保存的证据

每个下载文件都要记录：

- 素材来源页面 URL
- 实际下载 URL（如果能合法取得）
- 作品标题和作者/上传者
- 许可名称、版本和许可 URL
- 下载日期和复核日期
- 许可页面截图或 PDF
- 源文件 SHA-256
- 是否出现人脸、车牌、商标、门店或可识别地点
- 对源文件做过哪些修改
- 是否允许公开发布；无法确定时必须写 `false`

只要缺少其中关键项，就不能把该素材标记为“可发布”。可以在本机隔离目录中保留为内部测试候选，但不得混入正式可发布素材。

## 6. 主测试包设计

主测试包建议 11 段，每段约 4～9 秒，全部竖屏 `1080×1920`、H.264、30 fps、AAC 48 kHz。画面内容必须与预期作用一致；输入片不要烧字幕。

| clipId | 画面要求 | 预期作用 | 建议口播 |
|---|---|---|---|
| `wc-main-01-hook` | 泡沫覆盖或高压水流的强视觉开场 | `hook` | 你的车多久没有彻底洗过了？ |
| `wc-main-02-problem` | 明显泥点、脏轮毂或灰尘细节 | `problem` | 车身泥点和轮毂缝隙，普通冲水很难清理干净。 |
| `wc-main-03-service` | 洗车工位、车辆进场或完整服务环境 | `service` | 标准精洗，从预洗、冲刷到细节清洁一步完成。 |
| `wc-main-04-foam` | 均匀喷洒泡沫 | `process` | 先用泡沫软化车身表面的灰尘和污渍。 |
| `wc-main-05-rinse` | 高压水枪冲洗车身 | `process` | 再用高压水流冲净泡沫，减少泥沙残留。 |
| `wc-main-06-wheel` | 刷洗轮毂或轮胎边缘 | `detail` | 轮毂和轮胎边缘，也要逐处刷洗。 |
| `wc-main-07-interior` | 吸尘、玻璃或内饰清洁 | `detail` | 玻璃和内饰细节，同样认真处理。 |
| `wc-main-08-result` | 干净车漆、擦亮或抛光后的效果 | `result` | 清洁完成后，车身恢复干净透亮的质感。 |
| `wc-main-09-transition` | 从过程切到结果的行驶、转场或车身掠影 | `transition` | 接下来，一起看看清洁后的整体效果。 |
| `wc-main-10-offer` | 洗净车辆背景加测试优惠画面 | `offer` | 测试门店新客体验价十九块九，本素材仅用于系统测试。 |
| `wc-main-11-cta` | 到店、导航或门店入口画面 | `cta` | 点击导航到店体验，本素材仅用于系统测试。 |

`offer` 和 `cta` 不能只靠口播。为了让画面分析有足够证据，可在画面中加入明确但不冒充真实商家的测试卡：

- `测试数据｜新客体验价 19.9`
- `测试数据｜点击导航 到店体验`

测试字卡是画面内容，不是被测程序生成的字幕。它必须始终带“测试数据”标识，避免被误认为真实价格或真实门店承诺。

AI 的具体排序不是要求逐项等于表格顺序，但营销结构至少应表现为：钩子/问题靠前，服务、过程和细节居中，结果在清洁过程之后，优惠和到店引导靠后。

## 7. 异常测试包设计

异常包不要与主包一起跑。每个场景单独建立测试项目，方便定位失败原因。

| clipId | 制作方法 | 要验证的行为 |
|---|---|---|
| `wc-edge-01-silent` | 保留合法视频流，移除音轨 | ASR 能处理无语音片段；画面分析仍给出说明和作用 |
| `wc-edge-02-av-conflict` | 内饰吸尘画面，口播故意说“正在高压冲洗车身” | 系统按“画面行为优先”理解，不被冲突口播完全带偏 |
| `wc-edge-03-low-volume` | 将口播音量降低并混入轻微环境噪声 | ASR 失败或低置信时错误可见、可重试，不伪造转写 |
| `wc-edge-04-duplicate-a/b` | 同一源文件生成两份、上传为两个独立片段 | 两个不同 `clipId` 在最终顺序中各出现一次 |
| `wc-edge-05-long-speech` | 8～12 秒连续口播，包含两个短句 | 字幕能合理分段，没有截断、重叠或超长单行 |
| `wc-edge-06-unsupported` | 仅在隔离目录准备损坏/不支持文件，不混入正常包 | 上传阶段直接返回原始错误，不留下半批已提交素材 |

`wc-edge-02-av-conflict` 是专门的对抗性测试数据，必须在清单中标记 `intentionallyMisleading: true`，不得误用为正常营销素材。

## 8. IndexTTS2 执行步骤

### 8.1 启动与检查

1. 双击 `start_api.bat`，等待服务启动。
2. 在 PowerShell 执行：

```powershell
Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:9010/api/health'
Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:9010/api/voices'
```

3. 若首次请求触发模型加载，耐心等待，但不要反复启动多个实例。
4. 若失败，原样保存服务返回的 `code`、`message`、HTTP 状态和控制台输出，不要改写成“合成失败”这一类泛化文案。

### 8.2 声音选择

- 主测试包统一用一个中文普通话声音，建议自然、真诚、略有活力，不用夸张叫卖腔。
- 只有在确认内部测试边界后，才能临时使用内置声音样本。
- 如果用户提供了授权参考音频，优先调用 `/api/references` 注册该声音，再进行合成。
- 全部片段保持同一声音、近似音量和语速，避免声音变化干扰 ASR 与排序测试。
- `speed` 建议保持 `0.95～1.05`；不要仅为塞进口播把速度调到难以理解。

### 8.3 合成请求示例

先读取 `/api/voices` 的实际返回值，再把对应声音标识填入请求。不要凭文件名猜测 API 标识。

```powershell
$body = @{
  text = '你的车多久没有彻底洗过了？'
  voice = '<从 /api/voices 响应中复制的声音标识>'
  speed = 1.0
  emotion = @{
    mode = 'text'
    text = '真诚、清晰、有一点活力的洗车广告口播'
    weight = 0.5
  }
} | ConvertTo-Json -Depth 5

$result = Invoke-RestMethod `
  -Method Post `
  -Uri 'http://127.0.0.1:9010/api/tts' `
  -ContentType 'application/json; charset=utf-8' `
  -Body $body

$result
```

当前服务成功时会返回音频路径以及 `/api/audio/{audio_id}` 形式的访问地址。把每段 WAV 复制到 `tts\wav`，文件名与 `clipId` 一致。

### 8.4 每段音频的人工检查

- 文案完整，没有漏字、吞字和重复。
- 数字“19.9”读作“十九块九”，避免 ASR 因读法不一致产生无意义偏差。
- 没有开头静音过长、尾字被截断、明显爆音或削波。
- 音量相近，手机外放可以听清。
- 口播长度不超过所配画面的可用长度。
- WAV 原始输出保留，不覆盖，后续调整通过新文件版本完成。

## 9. 视频制作规范

### 9.1 处理原则

- 永远保留 `sources\original` 中的原文件不变。
- 先生成口播并测量时长，再选择略长于口播的画面片段。
- 裁成竖屏时等比缩放并居中裁切，不拉伸车身。
- 输入片不烧录字幕；仅 `offer`、`cta` 可添加带“测试数据”字样的画面卡片。
- 主测试包用 TTS 替换源音轨，避免第三方音乐版权和原口播干扰。
- 如源视频不足 1080p，可保持合理清晰度，不以虚假“4K 修复”冒充原始质量。

### 9.2 建议输出参数

```text
容器：MP4
视频：H.264 / yuv420p / 1080×1920 / 30 fps
音频：AAC / 48 kHz / 192 kbps / stereo 或 mono
时长：主包通常 4～9 秒；长口播边界片可到 12 秒
Web 优化：faststart
```

FFmpeg 合成示意，执行者应根据真实源尺寸、起止时间和口播长度调整：

```powershell
ffmpeg -ss 00:00:02.000 -i source.mp4 -i wc-main-01-hook.wav `
  -filter_complex "[0:v]scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,fps=30[v]" `
  -map "[v]" -map 1:a:0 -shortest `
  -c:v libx264 -pix_fmt yuv420p -preset medium -crf 20 `
  -c:a aac -ar 48000 -b:a 192k -movflags +faststart `
  wc-main-01-hook.mp4
```

如果口播比画面长，优先换更长画面或缩短文案；只有轻微差异才使用循环尾帧或合理的画面延长。不要把语音极端加速，也不要无提示截断尾字。

### 9.3 媒体探测

每个输出片都运行 `ffprobe` 并把 JSON 保存到 `probe`：

```powershell
ffprobe -v error -show_format -show_streams -of json wc-main-01-hook.mp4
```

必须确认：

- 视频和音频流均可解码。
- 分辨率、帧率、编码和采样率符合约定。
- 实际时长大于 0，音频没有比视频更早被截断。
- 文件可以在本机播放器中从头播放到尾。

## 11. 真实端到端测试步骤

### 11.1 测试前检查

- 程序不是演示模式，真实模型链路已启用。
- Qwen3-ASR 网关可达并成功加载模型。
- 视觉/编排所用中转模型配置有效，通信测试成功。
- FFmpeg、Remotion 和本地存储目录可用。
- 测试磁盘空间充足。
- 主测试包的授权清单、媒体探测和人工试听已经通过。

### 11.2 主包测试

1. 新建专用测试项目，例如 `真实链路-主包-v1`。
2. 严格按 `main-upload-order.json` 的乱序一次性上传全部主包片段。
3. 记录程序为每次上传分配的真实 `clipId`，另存“测试包 ID → 程序 clipId”的映射。
4. 点击一次生成，观察批量进度：媒体检测、音频提取、语音转写和画面分析。
5. 检查每段素材都有可读内容说明和九类之一的广告作用。
6. 检查 ASR 结果是否覆盖 `expectedAsrKeywords`；不要求标点逐字相同。
7. 等待自动排序、时间线、字幕、无字幕成片和带字幕成片全部完成。
8. 下载或播放两份 MP4，从头到尾人工检查。
9. 把最终 `finalClipOrder`、字幕、输出媒体信息、模型错误和界面截图保存到 `reports`。

### 11.3 异常包测试

- 每个异常场景单独建项目，不与主包混合。
- 记录程序是成功降级、等待恢复、可重试失败，还是不可重试失败。
- 错误报告必须保留原始 `code`、`message`、阶段、HTTP 状态、traceId 和可重试语义。
- 若程序表现与预期不符，先保留现场和复现步骤；此任务不授权直接修改业务代码。

### 11.4 当前中转站不稳定的特别说明

当前使用的模型中转站稳定性不足，测试期间可能多次出现无法服务、连接超时、流式响应中断或短暂恢复后再次失败。这类情况不一定是本地程序故障，也不能据此声称真实 AI 链路已经通过或永久失败。

执行测试的 AI 应这样处理：

- 保存每次失败的发生时间、处理阶段、原始 `code`、`message`、HTTP 状态、traceId 和是否可重试，不用“模型调用失败”等笼统文字覆盖原始错误。
- 让程序按照现有的受控重试和服务恢复机制继续等待，不要连续点击“生成”或新建重复任务。
- 中转站恢复后，检查程序是否从已经保存的片段进度继续处理，而不是重复分析已完成素材或产生重复 `clipId`。
- 如果经过多次中断后最终完成，测试报告写成“链路完成，但中转站曾不稳定”，并记录失败次数和大致恢复时间，不能写成“全程稳定通过”。
- 如果本轮一直无法完成，结果写成“被中转站不可用阻塞”，保留现场，等服务恢复后继续测试；不要在没有证据时直接判定为洗车编排程序缺陷。
- 未经用户明确同意，不擅自更换中转站、模型、密钥或付费服务，因为这会改变本次验收所测试的运行环境。

## 12. 验收标准

### 12.1 测试素材包验收

- 主包至少覆盖九种广告作用，每种至少一段，总数建议 11 段。
- 异常包至少包含静音、音画冲突、弱音、重复素材和长口播五类。
- 每段具有唯一测试包 `clipId`、可读说明、预期作用、口播、来源和授权记录。
- 每个网络源文件都保存来源页、许可页、作者、下载日期和 SHA-256。
- 所有输入片可解码；主包音画同步，口播无截断。
- 测试素材、授权证据和报告均位于 Git 项目外，没有误提交大文件。
- 所有未完成发布权复核的文件都标记 `testOnly: true`、`publishable: false`。

### 12.2 程序链路验收

设本次上传片段数为 `N`：

- `finalClipOrder.length === N`。
- 最终排序只包含本次任务的 `N` 个程序 `clipId`。
- 每个 `clipId` 恰好出现一次；不丢失、不重复、不引入其他项目素材。
- 每段都有可读的画面说明和有效广告作用。
- 营销结构总体符合“吸引注意 → 问题/服务 → 过程/细节 → 效果 → 优惠/到店引导”。
- 时间线严格按 `finalClipOrder` 读取用户上传的原始片段。
- 字幕来自真实 ASR，关键口播可识别，字幕没有明显截断或严重重叠。
- 无字幕和带字幕两份成片均可完整播放。
- 任何失败都保留上游原始错误内容和可重试语义。

## 13. 失败处理与停止条件

- 素材页面禁止 AI 使用、许可不清楚或需要额外授权：停止使用该文件，记录原因，换成自有或明确 Creative Commons 素材；不绕过条款。
- 内置声音授权无法确认：仅做内部测试并标记不可发布；需要上线素材时改用已授权声音。
- 下载页包含清晰人脸、车牌、商标或门店标识：优先换素材，不把裁切当作已经解决全部权利问题。
- IndexTTS2 失败：保存原始 API 和控制台错误；不要反复覆盖同名 WAV。
- FFmpeg 合成失败：保存完整命令、输入媒体探测和原始 stderr。
- Qwen 或中转模型不可用：记录健康状态和原始错误，按程序现有恢复机制等待；当前中转站可能反复无法服务，应按第 11.4 节区分外部依赖不稳定与本地程序缺陷，不要伪造“真实链路已通过”。
- 最终排序丢片、重片或跨项目取片：立即判定验收失败，保留项目数据、请求日志和输出，不继续公开使用成片。
- 执行过程中发现需要发布、上传、付费下载或使用个人敏感声音：暂停并向用户请求明确授权。
